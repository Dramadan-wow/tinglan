# 听澜中心服务器：运行、验证与 Linux 部署

本轮在原项目上新增独立 Qt 6.8 / C++17 服务端，将 Windows 的「TCP 聊天」页面接入中心服务器。原有会话、好友、群组、管理员和会员装扮功能保留。远程账号属于服务端，原课程演示账号不自动导入。

## Windows 编译

在项目根目录执行已有构建脚本：

```powershell
python scripts/build_gui.py
```

本机没有 PATH 中的 Python 时，可使用已经安装的解释器：

```powershell
& 'C:\Users\韩尚轩\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe' scripts/build_gui.py
```

使用当前 Qt 6.8.3 / MSVC x64 / CMake 配置，生成并部署 `bin/im_desktop.exe`、`bin/im_server.exe`。服务端使用同目录的 Qt Core/Network DLL 和 TLS 插件。复制软件时保留整个 bin 运行目录及所需配置，不要仅复制 exe。

根 CMake 的 `IM_BUILD_SERVER=ON` 启用服务端，原 Qt 桌面 preset 已启用。只构建课程 CLI 的默认配置不要求 Qt。

## 先创建两个远程账号

服务端停止时，在项目根目录执行：

```powershell
python scripts/create_remote_user.py alice
python scripts/create_remote_user.py bob
```

每次输入并确认自己设置的密码。密码为 12–128 UTF-8 字节，不在命令参数或日志中传递。账号固定为 3–32 位小写英文字母、数字、下划线，首位为字母；当前远程账号就是协议的稳定 userId，尚不提供昵称变更。

凭据写入 `server/data/users.json`，采用随机 32 字节盐、PBKDF2-HMAC-SHA256 600000 次迭代和 32 字节摘要。每次写入采用 QSaveFile 原子提交。服务运行期间占用凭据文件锁，创建账号会明确失败，避免配置与内存中的账号不一致。当前这是可测试的远程认证基础，没有在线注册、找回密码或远程管理 API。

## 启动服务端、连接两个客户端

```powershell
.\bin\im_server.exe --config .\server\config\local.json
```

也可以双击「启动中心服务器.cmd」。本地配置只监听 `127.0.0.1:56000`，并显式允许回环明文测试。停止前台服务端按 Ctrl+C。服务端记录连接、认证结果、消息 ID、转发和断开信息，不记录密码或聊天正文。

1. 双击「启动图形界面.cmd」，用原有本地账号进入主窗口，打开「TCP 聊天」。
2. 服务器填写 `127.0.0.1`，端口 `56000`，本机测试取消「TLS 加密」。填写远程账号 alice 和刚创建的密码，点击「连接并登录」。
3. 双击「启动TCP第二端.cmd」，使用另一份本地存档启动第二个窗口。进入相同页面，使用远程账号 bob 登录。两个窗口的本地课程账号不决定远程身份。
4. alice 窗口的收件人填 bob，bob 窗口填 alice。输入并发送文字，查看接收消息与服务器确认。
5. 关闭并重新启动服务端，两端应显示断开状态，并在 1、2、4、8、16、30 秒退避间隔自动重连、重新认证。
6. 点击客户端「断开」属于主动退出，会停止自动重连并清空页面密码；重新连接需要再次填写密码。

确认只表示服务器已将消息交给对方连接的发送队列，**不是对方已读或已永久保存**。离线收件人会返回失败；断线或确认超时会显示“送达状态未知”，客户端不会自动重发未确认聊天消息。

服务器地址和端口由页面配置，密码只保存在当前进程会话内，不写入本地配置。本阶段连接配置也不跨重启保存。

## TLS 使用

客户端默认勾选 TLS。只有数字回环地址且显式关闭 TLS 时允许明文；服务端也强制限制回环监听和回环连接。局域网、公网连接必须使用 TLS 配置。

将 production.example.json 复制为自己的 server.json，配置 PEM 证书链、PEM RSA/EC 私钥、数据文件路径及监听地址。代码要求 TLS 1.2 或更高版本。客户端校验证书链、有效期和主机名，不调用 ignoreSslErrors，也不会自动降级明文。服务端使用密码认证客户端，不要求客户端证书。

正式证书的 DNS 名称应与客户端填写的服务器域名匹配。自建 CA 测试时，在客户端选择信任的 CA PEM 文件；证书需要包含所连接域名或 IP 的 SAN。不要把测试目录中的一天有效测试证书用于正式部署。

Qt 运行环境需要可用 TLS 后端。Windows 构建脚本部署 TLS 插件；OpenSSL 后端还需匹配运行库，Schannel 后端使用系统能力。缺少 TLS 能力时程序会报错，不退回明文。

## Ubuntu 独立构建

当前 Windows 本机未提供可运行的 Ubuntu 环境，所以以下 Linux 编译和 systemd 运行步骤尚未实际验证。服务端目标只依赖 Qt Core/Network 和 C++17，源码未使用 WinSock、Windows CNG、Widgets 或课程 im_core。

准备 C++ 编译器、CMake、Ninja、OpenSSL 运行环境，以及 **Qt 6.8.x Linux gcc_64 SDK**。不要把 Windows 的 `.tools/Qt/.../msvc2022_64` 复制到 Ubuntu 使用。系统仓库的 Qt 版本可能低于 6.8，请检查版本。

```bash
sudo apt update
sudo apt install build-essential cmake ninja-build libssl-dev python3
# 将下方路径替换为自己安装的 Linux Qt 6.8 SDK 路径
export QT_ROOT="$HOME/Qt/6.8.3/gcc_64"
cmake -S server -B build-server -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_PREFIX_PATH="$QT_ROOT"
cmake --build build-server --parallel 4
export LD_LIBRARY_PATH="$QT_ROOT/lib${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"
export QT_PLUGIN_PATH="$QT_ROOT/plugins"
python3 scripts/create_remote_user.py alice --server build-server/im_server
./build-server/im_server --config server/config/local.json
```

也可在 server 目录执行 `cmake --preset ubuntu-release`、`cmake --build --preset ubuntu-release`，它们读取 QT_ROOT。先完成回环测试，再使用 TLS 配置监听实际网络。

## Linux 服务运行准备

`server/deploy/tinglan.service` 是部署模板。实际部署前应完成：

- 创建专用 tinglan 系统用户，将 Linux 可执行文件及匹配的 Qt 运行库放到 `/opt/tinglan`。
- 将配置放到 `/etc/tinglan/server.json`，证书和私钥放到配置指定位置；私钥只授予服务用户必要读取权限。
- 创建 `/var/lib/tinglan` 并授予 tinglan 用户写权限；以该用户身份离线创建账号。
- 配置 Qt 库与插件搜索路径或正确的 RPATH；模板没有假定机器上的 Qt 安装目录。如果 Qt 安装在 `/home` 下，模板的 ProtectHome 会禁止访问，应将运行依赖部署到 `/opt/tinglan`。
- 核对 TLS、网络端口和云安全组后，再安装 systemd 模板。

```bash
sudo cp server/deploy/tinglan.service /etc/systemd/system/tinglan.service
sudo systemctl daemon-reload
sudo systemctl start tinglan
sudo systemctl status tinglan
journalctl -u tinglan -f
sudo systemctl stop tinglan
```

本轮没有连接云主机、开放系统防火墙或安装系统服务。

## 自动测试与实际范围

```powershell
python tests/network_integration.py
python scripts/build_gui.py --test
```

集成测试使用临时随机密码、临时凭据存储和独立数据目录，不创建默认生产账号。它启动一个独立服务端、两个复用现有 MainWindow 的独立 Qt GUI 测试进程，以及原始协议测试连接；测试程序仅用于自动驱动真实界面，不是业务运行入口。

输出为 `tests/network-output/<时间戳>/results.json`、服务端日志、各窗口实际截图。TLS 测试通过 Python cryptography 生成一次性 CA 和证书；缺少该测试依赖会标记未验证。原有 GUI 回归报告位于 `tests/gui-output/`。最新实际验证结果参见「中心服务器验证记录.md」。

## 当前边界与下一阶段

- 支持在线一对一转发；还没有远程群聊、好友关系校验、消息持久化、离线消息和多设备会话。同一远程账号只允许一个在线连接。
- 远程账号、远程消息没有同步到原本地课程账号、会员、头像、背景或小火人数据。原本地普通密码存档仍是课程演示格式；服务端不会读取它。
- 服务端去重是内存中的 10 分钟窗口，最多 10000 条已转发消息；满时拒绝新消息，重启后清空。它不能提供跨重启的“恰好一次”保证。
- PBKDF2、连接数、消息频率、登录频率和发送队列有限制，但尚未做正式并发容量评估、审计告警和公网安全验收。
- 连接确认不是终端接收确认。下一阶段先实现持久化消息表和 `(senderId, messageId)` 唯一约束、事务提交、离线拉取与客户端接收回执，再迁移好友/群权限。
- 保留 network/ 作为移动端复用库，固定协议版本和兼容策略；Android/iOS 需各自工具链和前台/后台连接策略。手机 UI 可通过 QObject 适配层使用该网络库。

完成 Linux 实际编译、跨两台实体电脑的 TLS 测试和持久化后，再部署云端并开展更大并发测试。
