# 听澜统一平台：使用、实现与验证

本轮在原 Qt Widgets 界面上接入服务器业务，保留账号、好友、群组、消息和装扮界面。正式客户端不再需要进入独立 TCP 页面，也不显示服务器 IP 输入框。离线课程演示仍单独保留。

## 直接使用

1. 双击项目根目录的「启动中心服务器.cmd」，保持控制台窗口运行。
2. 双击「启动图形界面.cmd」，用原来的登录昵称、对应服务及密码登录。
3. 本机验证第二个用户时，双击「启动第二个客户端.cmd」。该入口使用另一份本机装扮/演示文件，避免两个窗口争用同一个文件锁；服务器账号和聊天数据仍完全相同。
4. 在普通「会话」页选择好友或群聊发送消息。到「微博广场」发布动态，另一个用户可实时看到并点赞、评论。
5. 在「账号」页选中服务行，点击「修改登录昵称 / 密码」。昵称在全平台唯一，保存成功后使用新昵称登录；只改昵称时密码字段留空。修改密码需要原密码，新密码至少 12 字节。

服务端首次启动会把 `bin/data/tencent_data.txt` 导入新建的 `server/data/workspace.sqlite`。导入不会删除或覆盖来源文件；数据库存在后不再重新导入。因此，之后修改旧本机存档或使用本机管理员重置密码，不会改变服务器账号。不要删除服务器数据库来“同步”旧文件。

如果原存档没有改过，课程示例用户是张三、李四、王五、赵六，示例密码 123456；王五选择微信，其余选择 QQ。已有改名、改密以自己的存档为准。新用户可在普通登录页创建账号，自动分配内部编号。

命令等价于在项目根目录运行：

```powershell
.\bin\im_server.exe --config .\server\config\local.json
.\bin\im_desktop.exe
.\bin\im_desktop.exe --data .\bin\data\second_client.txt
```

关闭客户端只会登出该用户。服务端控制台按 Ctrl+C 停止。后续重启服务器仍读取同一个 SQLite 数据库。测试脚本退出时会清理自己启动的进程，不会留下测试服务器。

原有「启动Qt演示.cmd」使用 `--offline-demo`，用于单机课程演示，其数据不与正式服务器同步。 离线窗口标题会标明“离线课程演示”，微博入口显示启动指引并禁用发布和刷新；不会再展示旧 TCP 登录表单。

## 配置与连接过程

- 客户端配置：`bin/client.json`，包含 host、port、tls、allowInsecureLoopback 和可选 caFile。只能由部署人员修改文件，普通页面不提供 IP 输入框。
- 服务端配置：`server/config/local.json`。默认仅监听回环地址的 56000 端口，供本机联调。
- 云端配置模板：`server/config/production.example.json`。外部网络必须启用 TLS，提供证书及私钥。客户端必须使用与证书匹配的域名/IP，并信任其 CA。
- 配置中的相对文件路径以配置文件所在目录为基准。

客户端读取配置，异步连接 TCP/TLS，提交昵称、所选登录服务和密码。服务器在线程池验证凭据，将连接绑定到内部稳定用户编号。客户端收到脱敏数据后打开原主窗口。私聊、群聊、好友申请、群管理及账号修改都发送统一命令，由服务器校验权限并提交 SQLite 事务，提交成功后确认并向相关客户端同步数据。

用户切换服务只改变业务视图，自动重连仍使用最初认证服务的凭据。昵称变更会更新重连昵称；修改认证服务的密码会更新重连密码。关闭用于认证的服务后需要重新登录其他服务。

## 协议与持久化

沿用协议 v1 外壳，每帧为 4 字节大端长度加 UTF-8 JSON，帧上限 64 KiB。所有请求有 UUID、type、senderId、recipientId、data。现有 login/login_result、heartbeat/error 保留。

平台登录在 login.data 中增加 `workspace:true`、`username`（登录昵称）、`password`、`service`；注册另加 `register:true`。成功返回 userId，例如内部 u10001，它不在普通界面显示。

普通业务使用 `workspace_command`，data 中的 op 包括：

- chat.send/read/star/recall；
- profile、account.edit/open/close/bind；
- friend.request/respond/cancel/remove/edit/block；
- group.create/invite/apply/cancel/approve/leave/disband/edit/admin/mute/kick/transfer/mode；
- feed.publish/like/comment/delete、sync。

`workspace_result` 返回 requestId、ok、必要的业务编号或错误说明。这是普通业务的保存确认。旧 TCP 测试模式仍支持 chat/message_ack，供历史协议回归，不是正式界面入口。

服务端始终用认证连接对应的 actor 调用业务层，自报 senderId 不符会拒绝。客户端不能通过换 target、service 或 senderId 绕过服务拥有权、好友、黑名单、群成员、禁言或帖子作者检查。

`workspace_sync` 分段发送 JSON 快照：snapshot UUID、part（从 0 开始）、count、Base64 payload。每段原始数据不超过 24000 字节，总快照最多 16 MiB，接收端验证编号、顺序、总量和 Base64。快照不含管理员凭据或用户密码摘要；私信仅对双方可见，群消息仅对成员可见。

SQLite 包含 state、operations、posts、likes、comments。state 保存原有业务模型的 JSON；operations 按 actor + 请求 UUID 保存摘要和结果，事务内去重，重启后仍有效。含密码的操作使用带盐慢摘要，避免保存原密码或快速密码校验值。收到确认意味着服务器已提交，不代表对方已经阅读。断线或确认超时会提示结果未知，不自动重发，以免重复；重新同步后核对结果。

## Ubuntu 编译与部署准备

需要 C++17 编译器、CMake/Ninja、Qt 6.8 或更高兼容版本的 Core、Network、Sql 及 SQLite/TLS 插件。不要假设 Ubuntu 系统自带 Qt 版本符合要求。服务器无需 Widgets、图形桌面或显示器；Windows CNG 分支在 Linux 下切换为 Qt 密码算法。

在已经安装 Qt SDK 的 Ubuntu 环境中：

```bash
export QT_ROOT=/opt/Qt/6.8.3/gcc_64
cmake -S server -B build-server -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_PREFIX_PATH="$QT_ROOT"
cmake --build build-server --parallel 4
export LD_LIBRARY_PATH="$QT_ROOT/lib:${LD_LIBRARY_PATH:-}"
export QT_PLUGIN_PATH="$QT_ROOT/plugins"
./build-server/im_server --config server/config/local.json
```

先用本机回环配置验证。正式部署将程序和所需 Qt 运行库放到 /opt/tinglan，配置放 /etc/tinglan/server.json，数据放 /var/lib/tinglan，给 tinglan 服务账号读配置、证书并写数据目录的权限。生产模板启用 TLS；私钥和数据库不得对其他普通用户开放。systemd 模板需按实际 Qt 部署方式设置库及插件路径，安装后使用：

```bash
sudo systemctl start tinglan
sudo systemctl stop tinglan
sudo systemctl status tinglan
journalctl -u tinglan
```

### 升级已部署的服务器

`server/deploy/update-server.sh` 用于已按上述目录部署的服务器原地升级。在 Windows 打包源码时必须保留 LF 换行，否则 `VERSION` 带回车，脚本会拒绝继续：

```bash
git -c core.eol=lf -c core.autocrlf=false archive --format=tar.gz -o tinglan-<版本>-server-source.tar.gz HEAD VERSION src workspace network server scripts/publish_client_update.py
sha256sum tinglan-<版本>-server-source.tar.gz Tinglan-<版本>-Client-Setup.exe client-update.json > SHA256SUMS
```

把源码包、`SHA256SUMS`、`update-server.sh`，以及可选的普通客户端安装包与 `client-update.json` 上传到服务器同一目录，用 root 运行 `bash update-server.sh`。脚本先核对哈希并在服务运行中编译，确认新程序版本后才停止服务；随后把数据目录、旧程序和 `server.json` 备份到 `/root/tinglan-backup-<时间>`，替换程序并启动，启动失败时自动换回旧程序。提供安装包时以服务账号发布客户端更新。脚本不改写配置、证书和数据库；Qt 路径、服务名等可用同名环境变量覆盖。

Ubuntu 24.04 云服务器已按上述方式部署，并用该脚本原地升级到 5.6.2。两台实体电脑和移动端的长期使用仍需继续验证。

## 当前限制与下一步

1. 消息已经持久化，但课程版仍在每次业务修改后保存整个业务 JSON，再同步当前用户可见快照。state 上限 8 MiB，用户上限 1000，帖子显示最新 40 条、每帖最新 10 条评论；不是大规模生产后端。下一步应将用户/好友/群/消息改为独立 SQL 表，消息及广场分页、增量事件同步，并为 operations 设计明确去重保留期限。
2. 登录凭据、好友/群/消息和广场统一；本机管理员、登录审计、充值核验、会员权益、自定义头像/背景等尚未迁移到中心服务。仍可演示，但不能声称跨设备一致。下一阶段优先补服务器管理员权限与审计、媒体上传以及会员权限的服务端验证。
3. 普通账号使用随机盐 PBKDF2-SHA256：新密码按 600000 次迭代保存，旧的 100000 次摘要仍可登录，并在下一次成功登录时于认证线程自动重算；注册、修改密码、开通服务和管理员重置的新密码至少 12 字节，已有的较短密码仍可登录。正式上线前应移除示例凭据，加入账号级登录限制、恢复机制及完整审计。当前认证在线程池执行；其他课程业务及部分密码编辑仍在服务器事件线程，需进一步限流与性能优化。
4. TLS 已有实测基础，但本机回环默认明文。局域网或云端不能直接照搬明文配置。还需要有效域名/证书、数据库备份与恢复演练、最小端口放行，以及两台真实设备验证。
5. 网络和 workspace 模块不依赖 Widgets，可供 Android/iOS Qt Quick/QML 客户端复用；当前四栏桌面 UI 不应直接缩小用在手机上。移动端、消息通知和离线缓存尚未实现。

先完成平台数据迁移/权限与审计，再做 Ubuntu/TLS 双机测试，最后部署公网；目前无需为了本机联调立即购买服务器。
